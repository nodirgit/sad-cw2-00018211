# Figure captions (for the report)

## Figure 2.1 — Overall architecture

The prototype is split into four layers so that each kind of change at the farm touches one place. The screens only call application services, and each service owns one farm job and its requirement: MortalityService the death log (FR-01), CrossCheckService the bazaar weights (FR-05), BatchProfitService the per-batch money (FR-03). The services depend only on the port interfaces (`Repository<T>`, `SensorProvider`, `LightController`, `VoiceParser`, `SpeechRecognizer`). Infrastructure classes realize those ports, and `app/container` is the one place that chooses them, so replacing the simulated sensors and relays with real ones, or browser storage with a server database, changes only infrastructure and the container. The domain sub-packages hold the farm's rules with no screen or storage code, which is why the 36 unit tests can check them against in-memory repositories.

## Figure 2.2 — Detailed class diagram (2.2a people, farm, partners, feed · 2.2b money and slaughter)

Composition encodes the farm's ownership rules: a `House` exists only inside the `Farm` and a `Batch` only inside its `House`, so every death, feed delivery, cost and sale is booked against one batch (FR-02, FR-03). A `HeadCountRecord` and its `HeadCountCorrection`s exist only inside their `SlaughterSession`, so a recount is added as a correction with a note and the crew's original figure is never overwritten (NFR-04). The `WeightTally` belongs to its session too, and `status()` gives MATCH only when the agent's and the representative's kg agree, which is the condition `CrossCheckService.recordSale()` needs before any sale is recorded (FR-05). Generalization carries the access and money rules: `User.canViewFinancials()` hides money from a `Worker` (NFR-03), and `FinancialEntry.signedAmount()` makes profit a single sum over `Expense` and `Sale`. Buyers are modelled as one `Buyer` class with a `BuyerGroup` attribute rather than a subclass per buyer type, because buyers are configuration the Director adds and edits in the app (NFR-05); `requiresCrossCheck()` reads the group, so only a Bazaar agent's sales wait for matching weights.
